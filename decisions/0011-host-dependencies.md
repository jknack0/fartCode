# ADR-0011: Host dependency detection + install/update/uninstall (E3-02)

- **Status:** Accepted
- **Date:** 2026-08-03
- **Ticket:** E3-02
- **Relates to:** E1-08 (onboarding), E3-01 (provider registry), E2-06
  (agent launch), E3-05 (network update checks)

## Context

E3-02 detects which agent CLIs are on the host and installs/updates/removes
them. The reference is a full `HostDependencyManager` runtime with
installations-per-dependency, path entry resolution, PTY install runners,
SSH execution contexts, and a network update service.

## Decision

- **`ade-core::dependencies`** — Phase-0 port in two files:
  - `host_dependency.rs`: `HostDependency` (id, name, detect_paths,
    version_command, min_version, install_plan), `InstallType`, `InstallPlan`,
    `DependencyStatus` (serialized to kv), TTL + kv prefix constants.
  - `mod.rs`: `InstallRunner` trait + `ProcessInstallRunner`, 7
    `DependencyManager` command builders (npm/pip/brew/cargo/go/curl/
    gh-release), `HostDependencyStore`.
- **Install metadata source of truth**: `install_metadata.json` committed in
  the module, regenerated by `install_metadata.py` from the reference
  `hostDependency` descriptors (21 npm packages, 14 curl/custom commands,
  github update repos). Merged with `ade-providers` binaries/names at
  runtime. This makes `ade-core` depend on `ade-providers` (a leaf data
  crate; no cycle).
- **Detection**: PATH scan of `detect_paths` (executable check), version
  probe `<binary> --version` when found (a failed probe yields
  `version: None`, never fails detection). Results cached in kv under
  `host-dep:<id>` with a 5-minute TTL; `refresh()` re-detects all 35 on app
  start (cheap — only installed binaries spawn a probe).
- **Install/update/uninstall**: run through the `InstallRunner` abstraction;
  Phase 0 streams child output into a caller sink (`ProcessInstallRunner`).
  The reference's visible-PTY install is E2-06's job — the sink is the seam.
  On success the runner re-detects (install/update) or clears the cache
  (uninstall). Curl-style installs run the reference's shell one-liner via
  `sh -c` (the reference uses the terminal shell profile).
- **Network update checks stubbed**: `latest_version` returns `None`
  ("unknown") until the npm-registry / GitHub-releases clients land (E3-05);
  the `update_repo` metadata is already carried for them.
- **No installer** (`rovo` et al.) → `install_plan: None`; the store returns
  a typed error for install attempts and no instructions.
- **`sh -c` note**: curl install commands are shell pipelines — they cannot
  run argv-style; the manager deliberately shells out exactly the reference
  command string. All other managers use argv arrays (no shell).

## Consequences

- Detection + cache + re-detect (acceptance 1 + 3) are fully testable with a
  scoped PATH (tests serialize PATH mutation via a mutex; the dev machine
  genuinely has claude/codex on PATH, so tests assert cache writes rather
  than machine-dependent flags).
- E2-06 consumes `InstallRunner` for the PTY install UI; E3-05 fills
  `latest_version`; E1-08's onboarding consumes `install_instructions`.
- 7 integration tests + 3 unit tests; smoke section 17 exercises detection
  end-to-end.
